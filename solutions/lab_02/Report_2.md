# Задание 1. Имена, ссылки и изменяемость

## Эксперимент A. Неизменяемый объект

### Прогноз

До `a += 1` имена `a` и `b` указывают на один объект `10`. После `a += 1` имя `a` будет указывать на новый объект `11`, а `b` останется связанным с `10`.

### Фактический результат

После `a += 1` значение `b` не изменилось. Идентификатор `id(a)` изменился, а `id(b)` остался прежним.

### Объяснение

`int` — неизменяемый тип. Операция `a += 1` не меняет объект `10` на месте. Она создаёт новый объект `11` и перепривязывает имя `a` к нему. Имя `b` продолжает ссылаться на старый объект `10`.

### Схема

```text
До:
a ─┐
b ─┘ → int 10

После a += 1:
b → int 10
a → int 11
```
## Эксперимент B. Изменяемый объект

### Прогноз

first и second будут указывать на один список. После second.append(30) изменение будет видно через оба имени. После second = [10, 20, 30] имя second будет указывать на новый список.

### Фактический результат

После second.append(30) список first тоже изменился. После second = list(first) список second стал отдельным объектом. first == second истинно, first is second ложно. Изменение нового second не повлияло на first.

### Схема до переназначения
```text
first ─┐
second ┘ → список [10, 20, 30]
```

### Схема после переназначения
```text
first  → список [10, 20, 30]
second → новый список [10, 20, 30]
```

###  Ответы на вопросы
1. Присваивание second = first не меняет сам объект. Оно только создаёт второе имя для того же объекта.
2. Операция над неизменяемым объектом приводит к созданию нового объекта, потому что старый объект нельзя изменить на месте.
3. Определить, что два имени обозначают один объект, можно с помощью is или сравнив id().

# Задание 2. Поверхностное и глубокое копирование

## Прогноз

- `alias` будет полностью совпадать с `original` (один и тот же объект).
- `shallow` будет иметь новый внешний список, но вложенные списки останутся общими с `original`.
- `deep` будет полностью независим от `original` на всех уровнях вложенности.


## Таблица сравнения способов копирования

| Операция | Новый внешний объект | Новые вложенные объекты | Изменения независимы                      |
|----------|----------------------|--------------------------|-------------------------------------------|
| Присваивание (`alias = original`) | Нет | Нет | Нет                                       |
| Поверхностная копия (`original.copy()`) | Да | Нет | Внешний список независим, вложенные общие |
| Глубокая копия (`copy.deepcopy(original)`) | Да | Да | Да                                        |

## Ошибочное создание матрицы

### Неправильный вариант

Использовалась конструкция:

```text
wrong_matrix = [[0] * 3] * 3
wrong_matrix[0][0] = 1
```

Внутренний список `[0, 0, 0]` создаётся **один раз**, затем три раза повторяется ссылка на него. Все три строки — один и тот же объект. Изменение `wrong_matrix[0][0]` меняет все строки.

### Правильный вариант

Использовалась конструкция:

```text
correct_matrix = [[0] * 3 for _ in range(3)]
correct_matrix[0][0] = 1
```

Здесь каждый внутренний список создаётся **отдельно** в цикле. Поэтому меняется только первая строка.

## 7. Ответы на вопросы

1. Поверхностная копия создаёт новый внешний контейнер, но вложенные объекты остаются общими. Глубокая копия рекурсивно копирует и вложенные объекты, делая структуру полностью независимой.

2. Глубокое копирование дороже по времени и памяти. Оно может копировать неизменяемые объекты без пользы, а также нарушать ожидаемое совместное использование данных (например, когда общий ресурс должен оставаться общим). Иногда глубокое копирование может привести к бесконечной рекурсии при циклических ссылках, если не настроено.

3. Если вложенные объекты неизменяемы (числа, строки, кортежи) или если вы не собираетесь изменять вложенные структуры, а меняете только внешний контейнер (добавляете/удаляете элементы). Поверхностная копия быстрее и экономичнее.

# Задание 3. Подсчёт ссылок и время жизни объекта

## Прогноз

При каждом новом имени или помещении объекта в контейнер счётчик будет расти. При `del alias` и `container.clear()` — уменьшаться. `sys.getrefcount()` всегда будет показывать на единицу больше реального числа ссылок в коде, т.к сама использует ссылку на объект. Слабая ссылка после `del record` вернёт `None`.

## Фактический результат

### Подсчёт ссылок

| Действие | Что происходит со счётчиком |
|----------|-----------------------------|
| `data = [1, 2, 3]` | Счётчик = 1 (имя `data`) |
| `sys.getrefcount(data)` | Счётчик = 2 (имя `data` + временный аргумент) |
| `alias = data` | Счётчик = 3 |
| `container = [data]` | Счётчик = 4 |
| `del alias` | Счётчик = 3 |
| `container.clear()` | Счётчик = 2 |


### Слабая ссылка

После `record = Record()` создаётся объект `Record`. Слабая ссылка `weak_record` не увеличивает счётчик. После `del record` сильных ссылок не остаётся, объект удаляется, и `weak_record()` возвращает `None`. Слабая ссылка может быть полезна, если дочерний объект ссылается на родительский, чтобы не создавать циклических ссылок.

## Ответы на вопросы

1. Когда счётчик сильных ссылок становится равен нулю и объект не входит в циклическую структуру, требующую вмешательства сборщика мусора.

2. Нет. CPython использует внутренние аллокаторы (pymalloc), которые могут оставлять память в своём пуле для повторного использования. Возврат ОС зависит от реализации и размера объекта.

3. Сильная ссылка удерживает объект живым, увеличивая его счётчик. Слабая ссылка не увеличивает счётчик и автоматически становится `None`, когда объект удалён.

# Задание 4. Циклические ссылки и сборщик мусора

Пороги поколений и текущие счётчики были выведены. После `del first` и `del second` объекты стали недостижимыми - счётчики ссылок остались ненулевыми, т.к списки ссылаются друг на друга циклически. Поколения нужны, чтобы сборщик мусора не тратил время на проверку всех объектов каждый раз. Новые объекты выгодно проверять часто. Долгоживущие объекты — редко. Это делает сборку быстрее и не мешает программе работать.

### Практическая задача: граф

После удаления имён `node1`, `node2`, `node3` и вызова `gc.collect()` циклические узлы были собраны. Узел `node4` остался доступен, потому что на него сохранялась сильная ссылка и он не входил в цикл.

## Схема графа

```text
     ┌─────────────────┐
     │                 │
     ▼                 │
  node1 ──→ node2 ──→ node3
                         
  node4   (независимый)
```

## Ответы на вопросы

1. Когда два или более объекта ссылаются друг на друга, образуя замкнутую цепочку. Внешних имён на такую цепочку может не остаться, но счётчики ссылок внутри цикла ненулевые.

2. Если объект находится в изолированном цикле, ссылки на него есть только внутри самого цикла. Программа не может до него добраться, но счётчик остаётся ненулевым.

3. Молодые объекты проверяются чаще, потому что большинство из них умирает быстро. Старые объекты проверяются реже, чтобы не тратить время на долгоживущие структуры.

# Задание 5. Исследование потребления памяти

### Размер отдельных объектов

| Объект | Примерный размер, байт |
|--------|------------------------|
| Пустой список | 56 |
| Список из 10 целых чисел | 136 |
| Кортеж из 10 целых чисел | 120 |
| Строка из 10 символов | 59 |
| Целое число | 28 |
| `None` | 16 |

**Объяснение:** размер контейнера включает только сам контейнер и ссылки на объекты, но не сами объекты.

### Рост списка

При добавлении 100 элементов размер менялся не после каждого `append`, а скачками. Типичная последовательность:

```text
len=0, size=56
len=1, size=88, change=32
len=5, size=120, change=32
len=9, size=184, change=64
len=17, size=248, change=64
len=25, size=312, change=64
len=33, size=376, change=64
len=41, size=472, change=96
len=53, size=568, change=96
len=65, size=664, change=96
len=77, size=792, change=128
len=93, size=920, change=128
```

**Вывод:** список резервирует память с запасом. Длина — сколько элементов реально добавлено. Объём выделенной памяти — зарезервированное место. 
### Сравнение `list(range(...))` и `range(...)`

| Сценарий | Размер внешнего объекта | Пиковая память |
|----------|--------------------------|----------------|
| `list(range(100_000))` | около 800 КБ | около 3 МБ |
| `range(100_000)` | 48 байт | меньше 1 КБ |

**Вывод:** `list(range(100_000))` создаёт 100 000 объектов `int` и список ссылок на них. Это требует нескольких мегабайт. `range(100_000)` хранит только параметры генерации и занимает 48 байт независимо от диапазона.

## Схема

```text
list(range(100_000)):
   список ──→ [ссылка, ссылка, ссылка, ...]   (100 000 ссылок)
                 │        │        │
                 ▼        ▼        ▼
               int 0    int 1    int 2    ...   (много объектов)

range(100_000):
   объект range хранит: start=0, stop=100000, step=1
```

## Ответы на вопросы

**Увеличивается ли размер списка после каждого `append()`?**

Нет. Python увеличивает размер порциями, резервируя память с запасом. Это снижает количество перевыделений памяти.

**Почему список резервирует место с запасом?**

Чтобы операции добавления были быстрыми. Если бы список перевыделялся после каждого `append`, сложность добавления была бы O(n) на каждый вызов. С резервированием средняя сложность — O(1).

**Чем длина списка отличается от объёма выделенной памяти?**

Длина — сколько элементов реально добавлено. Объём выделенной памяти — сколько места зарезервировано. Между ними может быть запас.

## Способы уменьшить потребление памяти

**Использовать ленивые последовательности.** Вместо `list(range(...))` применять `range`.

**Не делать глубокие копии без необходимости.** Поверхностная копия или совместное использование неизменяемых объектов экономнее.

**Учитывать резервирование памяти контейнерами.** Если размер известен заранее, можно помочь интерпретатору предсказуемо выделить память.

# Наиболее опасные ошибки при работе с изменяемыми объектами:

- считать, что `b = a` копирует объект, а не создает вторую ссылку на объект;
- случайно создавать общие вложенные структуры через поверхностное копирование;
- думать, что `del` удаляет объект, а не имя;
- забывать, что циклические ссылки требуют сборщика мусора;
- измерять память только через `sys.getsizeof()`, забывая о вложенных объектах.
